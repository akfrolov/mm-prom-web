## 1. Роль фичи

Появляется второй статический коллекционный маршрут сайта: страница каждого
не-брендбук объекта `src/pages/obekt/[id].astro` → `/obekt/<id>/` (31 URL =
27 текущих + 6 новых − 2 брендбука `atlas-garazhny`, `avrora-vitebsky`).
Страница — единственный «карточный» контент-объект сайта: на неё ведут
карточки (главная, ленты аренды/продажи, каталог), маркеры и кнопки карты
каталога, попапы карт услуг; она заменяет битую `/kartochka-obekta/` и
внешние страницы invest-platforma как целевую для всех не-брендбуков
(решение владельца п. 6 «Решений по открытым вопросам»).

CR задаёт минимальный состав страницы: первый экран с фото и ключевыми
параметрами, характеристики, описание, расположение на карте, похожие
объекты, призыв оставить заявку; галерея из `images`; SEO (поисковые
заголовок/описание, canonical, OG-изображение — фото объекта); 404 для
неизвестного id. Брендбук-объекты на `/obekt/` не попадают — их полные
страницы остаются прежними маршрутами.

## 3. Целевой контракт маршрута

### 3.1 Роутинг и генерация

| Правило | Значение |
|---------|----------|
| Файл | `src/pages/obekt/[id].astro` — единственный новый файл-маршрут фичи |
| Генерация | `getStaticPaths` из `getCollection('objects')`; записи `id === 'atlas-garazhny'` и `id === 'avrora-vitebsky'` исключаются (их страницы брендбуков — `/atlas-garazhnyj/`, `/avrora-vitebskij/`, владелец — фича `brandbooks`) |
| Объём | 31 URL после фичи `objects-data` (33 записи − 2 брендбука); до её мерджа — 25 URL (27 − 2), это ожидаемо для изолированного прогона |
| Формат URL | directory-формат `/obekt/<id>/` — config уже обеспечивает: `trailingSlash: 'always'`, `build.format: 'directory'` (index.html в директории) |
| Иды URL | id записи коллекции = имя JSON-файла (kebab-case, стабильные); новых 6: `rabochaya`, `nevelskaya`, `kolpino`, `metallostroy`, `murino`, `ip-razmetelevo`; включая не-брендбук `voyskovitsy-park` |
| `/obekt/` «голый» | 404 (index-страницы семейства нет — это нормально, ссылки в каталог/объекты всегда с id) |
| Неизвестный id | `/obekt/<unknown>/` → 404: маршрут статичен, страница не генерируется → статический 404 (`404.astro`, noindex). Отдаётся стандартной 404-страницей сайта с HTTP-статусом 404 |
| 301 | для новых маршрутов редиректы не требуются (CR «Влияние на данные/миграции»); WP-301-карта CR-2026-001 не затрагивается |
| Sitemap | `@astrojs/sitemap` подбирает построенные URL автоматически → после build в sitemap должны оказаться все 31 `/obekt/<id>/` — это критерий приёмки CR и пост-чек build |

### 3.2 SEO / canonical / OG (правка `BaseLayout.astro`)

На страницу действуют те же env-правила BaseLayout: prod — `index, follow`
+ Метрика; staging (`MMPROM_ENV=staging`) — `noindex, follow`, без Метрики
(механика `site-shell` фичи, у страницы своей логики нет).

В `Props` BaseLayout добавляются опциональные свойства (CR «Влияние на
архитектуру»: «OG-пропсы в BaseLayout — изображение и тип для объектов и
статей»), остальные — без изменений:

| Проп | Тип | Дефолт | Использование |
|------|-----|--------|---------------|
| `ogImage` | string (путь/URL) | `/mmprom-logo.png` (как сейчас) | `og:image` = `new URL(ogImage, Astro.site).href` |
| `ogType` | string | `articles` переиспользуют со значением `'article'`; страницы объектов значение не передают → `website` | `og:type` страницы |

- `og:image` страницы объекта — **фото объекта**: `images[0] ?? image`
  (первое фото галереи; у записей после `objects-data` оба поля локальные
  пути `public/…`), абсолютный URL через `new URL(_, Astro.site)`.
- `og:site_name`, `og:locale`, canonical, robots — без изменений.
- Файл `BaseLayout.astro` правят и другие фичи (site-shell — шапка/подвал;
  articles — те же OG-пропсы): расширение Props вносится один раз в блоке
  B1 этой фичи, повторное использование — фичей `articles`; очерёдность
  правок одного файла решает план спринта.

Семантика `searchTitle` не меняется: это строка поиска каталога
(`searchTitle ?? title.toLowerCase()` в `ObjectCard`), а не SEO-поле;
страница его не использует.

### 3.3 Поисковые заголовок и описание страницы

| Мета | Значение по умолчанию (данные) | Опциональный оверрайд из записи |
|------|-------------------------------|--------------------------------|
| `<title>` | `{d.title} — карточка объекта — ММ Пром` (форма `<title>` эталонного мокапа: «Атлас Гаражный — карточка объекта — ММ Пром») | `hero.title` в тег не подставляется — `<title>` строится от названия записи; если владельцу нужен SEO-титул — поле появится/заполнится в `objects-data` (решение на ревью) |
| `description` | `d.desc` | `hero.text` |

Обрезки текста нет: `desc` у записей — 1–2 предложения, ок как
meta-description; полировка SEO-текстов — правка данных владельцем, не код.

### 3.4 Микроразметка (JSON-LD)

В `<Fragment slot="head">` страницы выводится один блок
`application/ld+json` с `@graph`:

- `BreadcrumbList`: Главная → Каталог → объект (последний пункт — canonical страницы).
- `RealEstateListing`: `name`, `description` (как meta-description), `url`, `image`
  (OG-изображение), `about` → `Place` с `PostalAddress` (`streetAddress` = `address`,
  регион по `location` (значения в данных сверены с адресами),
  `addressCountry: RU`), `GeoCoordinates` из `coords` и
  `floorSize` из `areaNum` (m², `unitCode: MTK`; при `null` — не выводится),
  `additionalProperty` — `PropertyValue` по всем `specs` (name/value).

`Offer` не выводится: цена у всех объектов «по запросу»; при появлении
числовых цен — добавить `offers` в тот же блок.

## 4. Целевая структура страницы (по мокапу `docs/mockups/kartochka_obekta.html`)

Разметка и стили страницы — внутри `[id].astro` (`is:inline`), данные —
через `define:vars` (ванильные скрипты, `prefers-reduced-motion` учитывается);
каркас — BaseLayout. Двухколоночный каркас мокапа `.object-shell`
(main + sticky aside 340px ≥1024: содержимое слева, CTA-панель справа;
<1024 — одна колонка + фиксированный CTA-бар снизу).

Порядок секций — по перечислению CR («первый экран с фото и ключевыми
параметрами, характеристики, описание, расположение на карте, похожие
объекты, призыв оставить заявку»); мокап-порядок (head → location →
price-params) отличается — CR приоритетнее мокапа (см. §5, расхождения).

| # | Секция | DOM-якорь | Блок | Содержимое из данных |
|---|--------|-----------|------|----------------------|
| 1 | Хлебные крошки | `#breadcrumbs` | B1 | компонент `Breadcrumbs.astro` (создаётся фичей `site-pages`); цепочка: Главная `/` → Каталог `/katalog/` → название записи; при отсутствии компонента — собственная разметка `.b-breadcrumbs` (та же структура §1.5 site-pages) |
| 2 | Первый экран — фото | `#gallery` | B2 (ветка «одно фото»/«заглушка» — уже в B1) | галерея из `images` / одно фото + подпись / заглушка; см. §6 |
| 3 | Заголовок объекта | `#object-head` | B1 | чип типа (`badge--<type>` из `object-card.css`, текст `typeLabel`, цвета п. 15 — канон object-card), h1 (`hero.title` ?? `d.title`), мета-строка: адрес · район (`address` · `district`), лид — краткое описание `desc` (единственное место короткого описания на странице) |
| 4 | Ключевые параметры | `#key-params` | B1 | meta-лист из первых 3 записей `specs` (иконка Material Symbols + подпись + значение; имя иконки — только из набора Material Symbols, иначе рендерится текст лигатуры); строка `specs` с площадью (подпись содержит «площад», значение совпадает с `area` или начинается с него и уточнения через `,`/`:`/тире) отбрасывается — площадь выводится одной плиткой, её уточнение («16 000 м², вакантно от 877 м²») переносится в значение плитки «Площадь»; иначе плитка показывает `area`; + «Цена» (`price`, `"по запросу"` при пустом); busy: примечание «Нет свободных площадей» |
| 5 | Характеристики | `#specs` | B1 | таблица `.specs-table` по мокапу (th = label, td = value; `< 768` — карточки-пары, как в мокапе); иконка из specs в таблице не рендерится (декор мета-листа №4 — решение на ревью) |
| 6 | Описание | `#about` | B1 | «Об объекте»: только при заполненном `hero.text` (уникальный полный текст, h2 «Об объекте»); без него секция не выводится — `desc` уже показан лидом в шапке, один абзац дважды не дублируется |
| 7 | Расположение | `#location` | B2 | карта во всю ширину контентной колонки; адрес и район под картой не повторяются — они в шапке (`#object-head`), площадь — в ключевых параметрах; карта — §7 |
| 8 | CTA-панель заявки | `#cta` (aside `.cta-card` / моб. `.cta-bar`) | B1 | заголовок/текст (`cta.title`/`cta.text`, дефолт — «Нужна консультация по объекту?» / «Ответим по ставке, коммуникациям и срокам заезда» по мокапу), кнопка «Получить консультацию» → форма №34, телефон `tel:88003331010`; скрытая передача объекта в форму — вне CR (§9) |
| 9 | Похожие объекты | `#similar` | B2 | «Похожие объекты» (мокап `section--tint`): сетка до 2 карточек `ObjectCard` (`showMap=false`, ленточная ветка), внизу «Смотреть все объекты» → `/katalog/`; логика выбора — §8 |

Демо-секции мокапа **не переносятся** (нет данных в коллекции, CR не
требует): «Свободные лоты» (`#lots`), «Преимущества» (`#advantages`),
«Поэтажные планы» (`#plans`), «Варианты использования» (`#use-cases`), «Аренда
и продажа на ваших условиях» (`#terms`), «Кейсы с этим объектом» (`#cases`),
микроразметка schema.org (`#microdata`) — см. §5 и §12. Зарезервированные
поля работают так:

- `faq` записи — при заполнении рендерится блок аккордеона (`details/summary`
  по мокапу `b-faq`/FAQ, после секции `#location`); при пустом — секции нет
  (сейчас 0/27 — отсутствует на всех 31 странице). Заполнение — фича
  `objects-data`, вёрстка ветки обязательна (контракт схемы уже есть).
- `hero` `{title, text, image}` — оверрайды заголовка/текста/главного фото
  первого экрана; при заполнении `hero.image` — он как главное фото галереи.
- `cta` `{title?, text?, href, label}` — оверрайд заголовка/текста CTA и
  опциональная дополнительная ссылка (`href`/`label`) рядом с кнопкой формы.

## 6. Галерея (B2) — ветки по данным

Источники изображений: `images` (галерея, массив локальных путей — добавит
`objects-data`) / `image` (фото карточки, есть у всех) / `placeholder`-текст.

| Ветки (по убыванию приоритета) | Условие | Рендер |
|--------------------------------|---------|--------|
| Мульти-галерея | `images` непусто и длина > 1 | главное фото `.gallery-media` + лента превью `.gallery-thumbs` (кнопки `.gallery-thumb` с `aria-pressed`, ≥768 — 5 в ряд по мокапу); клик по превью заменяет главное фото (inline-скрипт, без внешних либ); `alt` = название записи; главное фото — `loading="eager"`/высокий приоритет, прочие — `lazy` |
| Одно фото | ровно 1 фото (`images` ×1 или `image` при пустом `images`) | одно фото; подпись под/рядом с фото = `media.caption` (только если заполнена; п. 10 про карточки на страницы не переносится — тут подпись нужна по CR); без превью-ленты |
| Нет фото | `images` пусто и `image`/`hero.image` пусто | заглушка `.img-placeholder` (иконка + `placeholder` ?? название записи) — первый экран не останется пустым; превью-ленты нет |
| Битое фото | `img.onerror` | класс `is-broken` (скрытие битого img, как в ObjectCard) + видимой остаётся заглушка той же ветки |

После синхронизации `objects-data` реальный расклад: 6 новых записей —

## 13. Решения агента — на ревью владельца

1. **Порядок секций страницы** — по перечислению CR (gallery → head →
   key-params → specs → about → location → similar → cta), мокап-порядок
   (location и price до specs/about) вторичен; сетка мокапа
   (main + sticky-aside) сохранена. Если владельцу ближе мокап-порядок —
   перестановка секций локальна.
2. **CTA-панель: одна кнопка заявки** вместо мокап-пары («Обсудить проект» +
   «Получить презентацию» → гейт-брошюра): презентационная кнопка не
   включалась — `/gejt-broshury/` известная битая ссылка (план форм
   отдельно). Механика формы №34 — click-вариант с проверкой при
   реализации, фолбэк inline (§9).
3. **Превью галереи — кадры фото** (не иконки с подписями-алиасами как в
   мокапе): у данных нет алиасов кадров; поле алиасов можно добавить в
   `objects-data`, если важно.
4. **Логика «похожих»** — не определена CR: предложено приоритет типа + дозаполнение
   по близости площади (§8); альтернативы: только тот же тип, рандом/соседние
   по `sort`, явные поля `similar` в данных.
5. **`<title>` без подстановки `hero.title`** — поисковый титул всегда от
   названия записи (форма мокапа); SEO-титулы страниц полируются
   владельцем отдельно или полями `objects-data`.
6. **`ogType` для объектов не переопределяется** (остаётся `website`) — CR
   говорит про «изображение и тип», но для объектов явный тип не назван;
   статьи зададут `article` через тот же проп.
7. **`voyskovitsy-park` получает страницу** `/obekt/voyskovitsy-park/`
   (не брендбук; отдельно сохраняется в данных — CR решение п. 2).
8. **Компонент `site-pages` `Breadcrumbs`**: фича не ждёт его форс-мажорно —
   inline-фолбэк той же разметки допущен в B1.2; при мерже обеих фич остаётся
   один канон (проверять при ревью, что дубль разметки не остался).
